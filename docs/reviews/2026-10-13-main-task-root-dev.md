## Major
### 🟠 Test baru memakai path POSIX dan akan gagal di Windows, `scripts/dev-support.test.ts:35`
**Problem**: Test "accepts both the space and the equals form and resolves dirs against the cwd" memanggil `parseDevArgs(..., '/work', defaults)` lalu mengharapkan `stateDir: '/work/tmp/state'` dan `apiDir: '/abs/ws'`. Implementasi memakai `path.resolve`, yang di Windows menghasilkan `D:\work\tmp\state` dan `D:\abs\ws` (huruf drive ditambahkan, pemisah backslash). Saya memeriksa dengan `path.win32.resolve('/work', 'tmp/state')` yang menghasilkan `\work\tmp\state`, jadi pasti tidak sama dengan string di test.
**Why it matters**: Job `dev-lifecycle` di Windows menjalankan `bun run test` (yang memuat `scripts/dev-support.test.ts`) sebelum `bun test ... dev.test.ts`. Job itu akan berhenti di langkah "Fast tests", sehingga AC-9 untuk Windows tidak pernah dibuktikan, dan satu putaran CI terbuang. Test ini adalah test baru fitur ini, bukan test lama.
**Suggested fix**: Bangun nilai harapan dengan `resolve` atau `join` dari `node:path` (misalnya `resolve('/work', 'tmp/state')` dan `resolve('/abs/ws')`), atau pakai `cwd` dari `process.cwd()` dan bandingkan dengan `resolve(cwd, ...)`. Karena job Windows baru pertama kali menjalankan seluruh `scripts/*.test.ts` di Windows, jalankan workflow di branch percobaan sebelum merge; selain item ini saya menduga (tidak bisa saya buktikan dari macOS) `scripts/env-example.test.ts:60` (`expect(env.PATH).toBe(process.env.PATH)` gagal bila Bun di Windows mempertahankan nama variabel `Path` pada `Object.entries(process.env)`, sedangkan `process.env.PATH` tidak peka huruf). Lihat juga temuan Minor tentang perilaku Windows yang belum terbukti.

## Minor
### 🟡 `killTree` melewati proses group bila pemimpinnya sudah keluar, sehingga `ng serve` bisa tertinggal memegang port, `scripts/dev.ts:187`
**Problem**: `killTree` langsung `return` bila `running.done` (pemimpin group sudah mengeluarkan event `exit`). Rantai dev server adalah `bun run` (pemimpin group) lalu `ng serve` lalu `esbuild`. Bila hanya pemimpinnya yang mati, turunannya tetap hidup di group yang sama dan tidak pernah disinyal. Reproduksi: jalankan `dev`, `kill -9` pid dari baris `[dev] started web (pid n)`; supervisor mencetak `[dev] web exited with status 137; stopping`, `[dev] stopping`, `[dev] stopped`, keluar `1`, dan `ps` masih menampilkan `ng serve --host 127.0.0.1 --port <WEB_DEV_PORT>` (ppid 1, pgid sama dengan pemimpin) yang memegang port.
**Why it matters**: AC-7 menyatakan setelah penghentian "kedua port bisa di-bind dan tidak ada pid anak yang tersisa", termasuk untuk jalur "dev server berhenti sendiri". Test lifecycle tidak menangkapnya karena `killTree` di test mematikan seluruh group sekaligus. Dampak ke developer: `dev` berikutnya melapor `WEB_DEV_PORT=... is already in use` dan harus berburu proses manual. Di Windows `taskkill /T` berdasarkan pid pemimpin yang sudah mati juga tidak menemukan turunannya.
**Suggested fix**: Di POSIX, kirim sinyal ke group walau pemimpinnya sudah keluar (ESRCH sudah ditelan oleh `try/catch`; group id tidak bisa dipakai ulang selama masih ada anggota), dan setelah `waitFor` pemimpin, periksa `process.kill(-pid, 0)` lalu `SIGKILL` bila group masih ada. Tambahkan test: matikan hanya pemimpin dev server lalu pastikan port bebas.

### 🟡 Error spawn ditelan sehingga `cargo` yang tidak ada hanya menghasilkan "api build failed", `scripts/dev.ts:172`
**Problem**: Handler `child.once('error', ...)` di `startChild` hanya menandai `done` dan menyelesaikan status `127`; objek error (ENOENT, EACCES) tidak dicetak. Reproduksi: jalankan `dev` dengan `PATH=/usr/bin:/bin`; keluarannya hanya `[dev] building api`, `[dev] api build failed`, `[dev] stopping`, `[dev] stopped`, tanpa menyebut `cargo`.
**Why it matters**: Penyebab paling umum kegagalan di mesin baru, terutama Windows, adalah `cargo` atau `bun` yang tidak ada di `PATH`. Developer hanya melihat "build failed" tanpa jejak. Hal yang sama berlaku bila salinan binary tidak bisa dieksekusi: pesannya hanya `api exited with status 127 before it was ready`.
**Suggested fix**: Cetak `[dev] cannot start <command>: <error.message>` (atau lewat prefix layanan) di handler `error`, tanpa mengubah teks pesan di tabel spec yang lain.

### 🟡 `run:api` tidak meneruskan SIGTERM dan SIGHUP sehingga backend ditinggalkan, dan skrip ini tanpa test, `scripts/run-api.ts:9`
**Problem**: Skrip mengabaikan `SIGINT` (benar untuk Ctrl+C terminal) tetapi tidak menangani `SIGTERM`/`SIGHUP`, dan `cargo` tidak berada di group terpisah. Reproduksi: jalankan `scripts/run-api.ts`, kirim `kill -TERM <pid skrip>`; skrip mati, `target/debug/api` tetap hidup dengan ppid 1 dan masih menjawab di `APP_PORT`.
**Why it matters**: Penghentian lewat IDE, process manager, atau `kill` biasa (bukan Ctrl+C) meninggalkan backend yang memegang port. Spec hanya meminta SIGINT diabaikan, jadi ini celah desain, bukan penyimpangan; tetapi akibatnya sama dengan masalah yang ingin dihindari fitur ini. Selain itu `run-api.ts` punya cabang sendiri (error spawn keluar `1`, status sinyal `128 + n`, `.env` default boleh tidak ada) dan tidak ada satu pun test; AC-2 menyerahkan bukti task berprasyarat `env` ke test fiturnya, sedangkan task `run:api` tidak punya.
**Suggested fix**: Teruskan `SIGTERM` dan `SIGHUP` ke anak (`child.kill(signal)`), tetap mengabaikan `SIGINT`, lalu tambahkan test kecil (env sementara, port bebas, tunggu `api listening on`, kirim SIGTERM, pastikan skrip dan backend mati dan status `143`).

### 🟡 Tidak ada pengaman untuk exception: error di tengah jalan atau saat bersih-bersih membiarkan anak yang `detached` hidup, `scripts/dev.ts:238`
**Problem**: Tidak ada `try/catch` di `main()`, `reload()`, timer watcher, dan `stop()`, serta tidak ada `uncaughtException` atau `process.on('exit')`. Contoh yang bisa terjadi: konstruktor `Supervisor` memanggil `rmSync(binDir)` (baris 238 sampai 239) yang di Windows melempar EBUSY bila ada `.exe` sisa yang masih berjalan (skenario run lama yang dibunuh paksa dengan `APP_PORT` berbeda sehingga preflight tidak menangkapnya); `stop()` memanggil `rmSync(this.binDir)` tanpa retry (baris 581) setelah `removeCopy` menyerah, sehingga `stop()` menolak sebelum `finished()` dan `[dev] stopped` tidak tercetak; `scan()` memanggil `statSync` untuk `Cargo.toml` dan `Cargo.lock` setelah `existsSync` tanpa `try/catch` (baris 465), berbeda dengan cabang berkas biasa di baris 454; `reload()` memanggil `statSync(executable)` dan `copyFileSync` tanpa penjaga.
**Why it matters**: Seluruh anak dijalankan `detached`, jadi supervisor yang jatuh karena exception tidak ikut membawa mereka; backend dan dev server tetap memegang kedua port (invarian spec: tidak meninggalkan proses anak). Pada sebagian jalur supervisor juga keluar tanpa pesan `[dev]` yang bermakna.
**Suggested fix**: Bungkus pembersihan awal dan akhir (`rmSync`) dengan try/catch yang tidak fatal, pakai `try/catch` yang sama di `statSync` untuk dua berkas akar, dan pasang satu pengaman terpusat (`unhandledRejection`/`uncaughtException`) yang mencetak `[dev] internal error: ...` lalu memanggil `stop(1)`; atau cukup bungkus `void this.reload()` dan `void this.start()` dengan `.catch(...)` yang memicu `stop(1)`.

### 🟡 Semua kegagalan baca file env dilaporkan sebagai "not found", `scripts/dev.ts:602`
**Problem**: `catch {}` di sekitar `loadEnvFile` mengubah setiap error (EACCES, EISDIR, dan lain-lain) menjadi `[dev] .env not found; copy .env.example ...` atau `[dev] env file not found: <path>`. Reproduksi: `bun --no-env-file scripts/dev.ts --env-file /private/tmp` mencetak `[dev] env file not found: /private/tmp` walau path itu ada (sebuah direktori). `loadEnvFile` sendiri sudah membedakan keduanya (`cannot read env file <path>: ...`).
**Why it matters**: Pesan menyesatkan: developer menyalin `.env.example` ke `.env` yang sudah ada tetapi tidak terbaca, atau mencari file yang sebenarnya ada.
**Suggested fix**: Tangkap error, tampilkan pesan tabel hanya untuk ENOENT (`error.message.startsWith('env file not found')`), dan untuk yang lain cetak `[dev] cannot read env file <path>: <alasan>` dengan status `1`. Tambahkan satu baris di tabel spec bila perlu.

### 🟡 Klaim "tanpa Docker" untuk `bun run test` hanya berlaku di CI, `scripts/db.test.ts:39`
**Problem**: `SKIP_DOCKER_CLI = IS_WINDOWS || (!HAS_COMPOSE_CLI && process.env.CI === 'true')`. Di mesin developer tanpa CLI `docker` dan tanpa `CI=true`, 16 test di `scripts/db.test.ts` (Compose config dan "Docker is not running") gagal. Saya buktikan: `env -i PATH=/usr/bin:/bin:<bun> bun test --no-env-file scripts/db.test.ts` menghasilkan 94 lulus dan 16 gagal; dengan `CI=true` 94 lulus dan 16 dilewati. Task `test` terdaftar dengan prasyarat `-`, `docs/development.md` menulis "tanpa Docker", dan AC-2 meminta `bun run test` lulus tanpa Docker; test clean checkout tidak menyembunyikan `docker` dari `PATH`, jadi AC-2 untuk Docker tidak pernah diuji di Linux.
**Why it matters**: Dokumentasi dan AC-2 menjanjikan lebih dari yang dijamin. Cabang `CI === 'true'` juga berarti runner Linux CI yang kehilangan Docker akan diam diam melewatkan test itu bila CI diset. Hasilnya bergantung pada lingkungan, bukan pada kontrak.
**Suggested fix**: Pilih satu kontrak dan tuliskan: (a) test Compose dilewati bila CLI tidak ada (`!HAS_COMPOSE_CLI`, tanpa syarat `CI`) dan job Linux `checks` menambahkan satu pengecekan eksplisit bahwa CLI ada supaya tidak lolos diam diam; atau (b) ubah tulisan di spec, katalog, dan AC-2 menjadi "tanpa daemon Docker" dan jadikan prasyarat CLI `docker` eksplisit. Bila (a), bukti AC-2 bisa memakai `PATH` tanpa `docker` di test clean checkout.
