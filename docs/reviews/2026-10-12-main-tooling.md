## Minor
### 🟡 ESLint warnings do not fail the lint gate, `package.json:27`
**Problem**: `lint` runs `eslint .` without `--max-warnings 0`, while the Clippy half runs with `-D warnings`. The effective config has at least one warn-level rule (`@angular-eslint/use-lifecycle-interface`), and ESLint 10 reports unused `eslint-disable` directives as warnings (`linterOptions.reportUnusedDisableDirectives` resolves to severity 1). I confirmed that a file containing a stale disable directive yields a warning and exit code 0.
**Why it matters**: The scope says lint must "run clean" on a clean checkout and on CI, and `AGENTS.md` states the Clippy-as-error policy. Today a warning can land through the pre-commit hook and CI unnoticed, so the two halves of `bun run lint` enforce different standards and warnings will accumulate.
**Suggested fix**: Add `--max-warnings 0` to the ESLint invocation and update the matching assertion in `scripts/tooling.test.ts` (the `lint` test currently only checks the Clippy half, so it will not notice).

### 🟡 Symlinks inside a generated root are invisible to the guard, `scripts/generated.ts:19`
**Problem**: `listFiles` only follows `isDirectory()` and `isFile()` dirents, so a symbolic link (to a file or directory) placed in a generated root is skipped entirely: it is neither hashed nor reported. I reproduced this in a scratch copy: after writing a valid manifest, adding `src/link.ts -> /etc/hosts` still exits 0.
**Why it matters**: The feature's requirement is that generated files are "rejected when edited by hand". A symlink is an edit the guard cannot see, and the file behind it would also be imported by TypeScript while being ignored by lint and format.
**Suggested fix**: Treat any entry that is neither a regular file nor a directory (symlink, socket, and so on) as a problem to report, or hash the link target path. Add a unit test for it next to the existing add, edit and delete cases.

### 🟡 The `check-generated` CLI wrapper has no test, `scripts/check-generated.ts:8`
**Problem**: `generated.test.ts` covers the library functions well, but nothing executes `scripts/check-generated.ts` itself. The failing path (stderr text, `process.exit(1)`, the `problem.replace(repoRoot, '')` path trimming) never runs because `packages/api-client` does not exist yet, and `tooling.test.ts` only asserts the `check` script string. `bun run check` therefore always exercises only the "root absent, return []" branch.
**Why it matters**: A regression in the 16-line wrapper (for example, the exit code dropped) would leave every test and `bun run check` green while the guard stops guarding, which is the exact requirement this feature closes.
**Suggested fix**: Add one process-level test that copies `generated.ts`, `check-generated.ts` and a `generated-roots.json` into a temp directory, creates a root with a tampered file, runs the script with Bun and asserts a non-zero exit and the expected stderr; and a passing run for the matching manifest.

### 🟡 `AGENTS.md` omits the new commands and the generator contract, `AGENTS.md:17`
**Problem**: The `## Commands` block lists build and test commands but none of the commands this feature adds: `bun run check`, `format`, `format:check`, `lint`, `typecheck`, `check:generated`. `bun run format` (the fix for a failing `format:check`) is not mentioned anywhere. The Rules say generated files are rejected when they do not match "the manifest written by the generator", but nothing says how a generator writes it: `writeGeneratedManifest` in `scripts/generated.ts` is exported and used only by tests, with no CLI and no mention in docs.
**Why it matters**: The scope's first checkbox is that the root `AGENTS.md` reflects the real stack and conventions, and agents work from the Commands block. An agent that sees the hook reject a commit has no documented fix, and the future generator feature (12) has to rediscover the manifest contract.
**Suggested fix**: Add the five or six task lines to the Commands block, with one comment saying `check` is what the hook and CI run and `format` rewrites files. Add one sentence to the generated-files rule naming `scripts/generated.ts` (`writeGeneratedManifest`) as the way a generator records its output.

### 🟡 Spec 0001 was edited to admit new dependencies, `docs/specs/0001-stack-audit-scaffold-workspace/index.md:55`
**Problem**: `@types/bun` and `@types/node` are not in the spec's Proposed stack; the change adds them and then adds a row to `index.md` and `rationale.md` ("Ditambahkan 2026-10-12 saat fitur 2") so the spec matches. The project rule in `AGENTS.md` is that new tools come only through a spec decision from `/architect`, and the review brief says no technology outside spec 0001 may be added.
**Why it matters**: The packages are type definitions only for already chosen tools, and the stated reasons are sound (typecheck of `scripts/` needs them, and `@types/node` is pinned to the Node 24 line instead of 26). But a retroactive spec edit by the implementing step turns the spec from a gate into a record, and the user's own constraint was explicit. I cannot tell from the repo whether the user approved it.
**Suggested fix**: Confirm with the user that this addition is accepted (or route the row through `/architect`), so the amendment has an owner. If accepted, no code change is needed.

### 🟡 The spec's flagged phantom-dependency gap is neither closed nor recorded as deferred, `docs/specs/0001-stack-audit-scaffold-workspace/index.md:220`
**Problem**: Spec 0001 lists as a negative consequence that the `hoisted` linker allows imports of undeclared dependencies and says "lint di fitur 2 perlu menutup celah ini bila penting". `eslint.config.mjs` has no rule for it, and neither `AGENTS.md` nor the scope records a decision to defer.
**Why it matters**: With a single hoisted `node_modules`, `apps/web` can import any package that happens to be installed at the root (ESLint, typescript-eslint, `@types/*` now sit there) and `tsc` and the build will pass. Closing it needs an import-plugin, which is new technology outside the spec, so the right move is a recorded decision, not silence.
**Suggested fix**: Record the decision (defer to a named later feature, or raise it with `/architect` for an `eslint-plugin-import`-style rule) in the spec follow-ups or the feature 2 scope item.

## Strengths
- Gates are defined once and reused: the hook, CI and the clean-checkout test all call `bun run check`, so there is no second definition of "clean" to drift. `tooling.test.ts` even asserts that every CI `run` line is a real root script or a `--locked` cargo command.
- The generated-root design keeps one source of truth (`generated-roots.json`) that ESLint reads directly, with the unavoidable Prettier copy guarded by a test, and the hash manifest distinguishes edited, added and removed files and reports all of them at once.
- The ESLint config does what the user chose and I verified it by probing: strict type-checked rules fire in `.ts`, inline templates and specs; template accessibility rules fire in `.html`; named-exports-only is enforced; `.mjs` and generated roots are handled separately.
- Earlier review points were acted on: the clean-checkout environment now strips `GIT_*` variables, the hook runs only the fast `check` instead of `test:scripts`, and the Rust test code is rustfmt clean. The new hook-rejection test proves the hook really blocks a badly formatted commit in a clean copy.
- `install-hooks.ts` never fails an install outside a git work tree or without git, and both paths are tested, including the stderr silence.
- The strict-lint retyping of the older tests (typed manifests instead of `Record<string, any>`, `satisfies` on the dependency field list) is behavior preserving; I compared each hunk and found no weakened assertion.
