# Review, main (workspace scaffold, spec 0001), 2026-10-12

**Reviewed by**: sonnet (author on opus)
**Scope**: 42 files (40 new, 2 modified; 88 vendored `.claude/skills/**` files and the two lockfiles were not reviewed line by line), uncommitted on `main`
**Verdict**: Approve with nits

## Summary
The change delivers feature 1 of the scope: exact toolchain pins, a virtual Cargo workspace with an Axum skeleton that listens on loopback and answers 404, an Angular 22.2.2 zoneless CSR scaffold under a Bun workspace, a Node runtime guard in front of every Angular script, and test suites that pin all of this down. I checked each file against spec 0001 (requirements, "Berkas yang dibuat fitur 1", key invariants) and found no deviation that breaks an acceptance criterion. All three suites pass here (`bun run test:scripts` 49 tests in about 11 s on warm caches, `bun run test:web` 2 tests, `cargo test --locked --workspace` 1 integration test). The findings are test-hardening and hygiene items, the main ones being rustfmt-dirty test code, a clean-checkout test that is not hermetic against git environment, and three spec'd checks that exist only as manual steps in `verify.md`.

## Minor
### 🟡 `apps/api/tests/skeleton.rs` is not rustfmt-clean, `apps/api/tests/skeleton.rs:41`
**Problem**: `cargo fmt --check` fails with five hunks in this file (around lines 41, 49, 66, 86, 92: calls longer than rustfmt's call-width heuristic that the author wrapped by hand or left on one line). `apps/api/src/main.rs` is clean.
**Why it matters**: The toolchain is pinned with `rustfmt` and `clippy` precisely so feature 2 can gate on them. The first `cargo fmt --check` gate will go red on code that shipped with this feature, and it would be reformatted in an unrelated commit.
**Suggested fix**: Run `cargo fmt` once and keep the result in this change.

### 🟡 Clean-checkout test is not hermetic against the caller's git environment, `scripts/clean-checkout.test.ts:13`
**Problem**: `childEnv()` copies the whole `process.env` into the `git init`, `git add --all`, and `git commit` calls that run in the temporary copy. Only `NODE_ENV` is removed. The commit also inherits the user's global git config.
**Why it matters**: When git runs a pre-commit hook it exports variables such as `GIT_INDEX_FILE` (and `GIT_DIR` in some contexts). Spec 0001 says feature 2 wires a native `core.hooksPath` hook that calls the same Bun tasks as CI. If `test:scripts` ever runs inside that hook, the `git add --all` in the temp dir would be directed at the real repository's index, and the "clean copy" check would be wrong or would corrupt the index. Separately, a user with `commit.gpgsign=true` would see the snapshot commit fail or prompt. This is latent today and only bites once the suite is called from a hook or an unusual shell.
**Suggested fix**: Build the child environment without any `GIT_*` variables, and add `-c commit.gpgsign=false` (and similar isolation such as a throwaway `GIT_CONFIG_GLOBAL`) to the snapshot commands.

### 🟡 Three spec'd runtime checks are manual only, `scripts/guard-node.test.ts:109`
**Problem**: The guard has good unit coverage and one process-level test under `bun --bun`, but the integration scenarios the spec names for AC-9 (`bun --bun run --filter web build` fails, and `bun run build:web` with a PATH that has no `node` fails) are only recorded as checked boxes in `verify.md`. Likewise AC-8's "no `apps/web/dist/web/server` folder" (the clean-checkout test only asserts `browser/index.html`) and AC-4's "`npm install` fails with `EBADDEVENGINES`" have no automated check.
**Why it matters**: The PATH-without-`node` case relies on Bun's behavior of silently substituting its own runtime, which is the exact external behavior this whole design depends on and the thing most likely to change in a Bun upgrade. Nothing in the suite would notice.
**Suggested fix**: Add a test that spawns Bun by `process.execPath` with a PATH that excludes `node`, runs the `web` build script, and expects a non-zero exit with a `guard-node:` message. The guard fails before `ng` starts, so it is fast. Add an `existsSync` assertion for `dist/web/server` after the build in the clean-checkout test.

### 🟡 `test:scripts` mixes millisecond unit tests with a network-dependent full build, `scripts/clean-checkout.test.ts:37`
**Problem**: `bun run test:scripts` runs the guard and pin tests together with a suite that does `bun ci`, a cold `cargo build --workspace` in a fresh target directory, and a production Angular build. It took about 11 s here only because the Bun and Cargo caches were warm; a cold run needs the registry and several minutes.
**Why it matters**: There is no script that runs only the fast tests, so any gate or hook that calls `test:scripts` (feature 2 plans a pre-commit hook on the same tasks as CI) inherits the slow, network-bound path.
**Suggested fix**: Keep the spec'd `test:scripts` meaning, but let the fast suites be run on their own (for example the clean-checkout file under its own name pattern or folder with its own script), and decide in feature 2 which of the two the hook runs. This touches the spec's `bunfig` and script table, so route it through `/architect` if you want it changed.

## Nits
- ⚪ `scripts/clean-checkout.test.ts:38`, `beforeAll` has no timeout argument, so Bun's default 5 s hook limit applies (I confirmed a 6.5 s hook fails with "hook timed out"). The copy takes about 0.3 s today, but it scales with every file git can see, including `.claude/skills`. Pass `STEP_TIMEOUT_MS`.
- ⚪ `scripts/test-helpers.ts:18`, `new URL(path, \`file://${repoRoot}\`)` does not escape the repo path, so a checkout under a directory containing `#`, `?`, or `%` resolves to the wrong file. `join(repoRoot, path)` is safer.
- ⚪ `scripts/workspace.test.ts:96`, the zone.js check matches only `"zone.js": ["zone.js@`. A nested entry such as `"@angular/core/zone.js": ["zone.js@...` (what a hoisting conflict looks like in `bun.lock`) would not match. Matching `["zone.js@` alone is stricter.
- ⚪ `scripts/pins.test.ts:7`, `EXACT_VERSION` rejects exact prerelease pins such as `22.0.0-rc.1`, which are exact versions by the spec's wording. Fine today, a surprise later.
- ⚪ `scripts/guard-node.mjs:71`, `runsAsScript()` returns `false` on any exception, so the guard would fail open (exit 0, no check) if the entry-point comparison ever throws. Unlikely in practice, but a guard that exists to stop a silent runtime swap should fail closed. The spec requires one file that is both importable and runnable, so the simplest mitigation is to treat an unreadable `argv[1]` as "run the check".
- ⚪ `scripts/guard-node.mjs:49`, nothing ties the `.nvmrc` major to the `<25` upper bound of `engines.node` (the guard and `pins.test.ts` check only the lower bound). Moving `.nvmrc` to Node 26 without touching `engines` passes every test.
- ⚪ `apps/api/tests/skeleton.rs:28`, `Server(child)` is built only after `read_line`, so a panic in `expect("read api stdout")` leaks the child. Wrap the child in `Server` straight after `spawn`. Also, the fixed port 3000 means `cargo test --workspace` fails whenever any other dev server holds it; the assertion message says so, and feature 3 should make the address injectable.
- ⚪ `apps/web/README.md:1`, kept per spec, but it tells readers to run bare `ng serve`, `ng build`, and `ng test` (the last one watches forever), which bypasses the Node guard and the `bun run` entry points. Worth a one-line pointer to `bun run build:web` and `bun run test:web` in feature 2 or 4.
- ⚪ `apps/web/src/app/app.html:1`, the Angular marketing placeholder (inline `<style>`, SVGs, external angular.dev links) is still there. Prettier `--check` also flags 8 scaffold files under `apps/web`; the spec defers formatting to feature 2, so this is only a reminder.
- ⚪ `.claude/skills/**` and `skills-lock.json`, committing them matches the spec's file table, so this is informational. They are 88 files (about 1 MB) of third-party content from six upstream repos, including two executable scripts (`gh-fix-ci/scripts/inspect_pr_checks.py`, `docker-compose-patterns/scripts/verify-compose.sh`) that agents run with the committer's rights. No symlinks, `package.json`, or lockfiles are inside, so the AC-3 and AC-4 scans are unaffected today, but a future skill update that ships a `package.json` with ranges or a `package-lock.json` would fail those project tests. Nothing verifies the hashes in `skills-lock.json`, and the upstream licenses have not been checked in this change.

## Strengths
- The Node guard is a pure `checkRuntime` function with the pinned values read from `.nvmrc` and `package.json` through `import.meta.url` (not the working directory), no hardcoded versions, and a regression test that runs it from a different cwd and under `bun --bun`.
- `scripts/pins.test.ts` and `scripts/workspace.test.ts` turn the spec's key invariants (exact versions, single lockfile, zoneless, strict, no NgModule, no SSR options, guard prefix on every web script) into executable checks, each tagged with the AC it covers.
- `scripts/clean-checkout.test.ts` copies exactly what git would commit, builds from the frozen lockfiles, and asserts `git status --porcelain` is empty afterwards, which is the right proof for reproducibility. The Rust integration test runs the real binary and covers the startup line, 404 on GET and POST, and the second-instance failure that names the address.
- `main.rs` matches the spec exactly (loopback only, no tracing or config, a bind failure that names the address and carries the OS error); manifests match the spec's tables value for value, and `Cargo.lock` resolves to the spec'd axum 0.8.9 and tokio 1.53.2.
- Spec, scope, and index edits are consistent with each other and with the code, and the decision log covers every mandatory decision from the brief.
