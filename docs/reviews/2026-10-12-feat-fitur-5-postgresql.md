## Summary

Kode cocok dengan spec sampai ke teks SQL, tabel pesan, argumen Compose, dan nama; saya tidak menemukan blocker maupun major. Temuan utamanya: `.env` belum diabaikan git di branch ini, `stop()` di harness tidak mencoba ulang saat `down` gagal dan menutupi pesan kegagalan awal, perlindungan log password di script init serta jalur konfirmasi interaktif `db:reset` tidak dikunci test otomatis, dan harness belum punya pagar bila test salah memanggil `db.ts` tanpa `COMPOSE_PROJECT_NAME`.

Yang saya jalankan sendiri: `bun run check` (exit 0, sekitar 5 detik), `bun test scripts/db.test.ts` (105 lulus), `bun test scripts` (190 lulus), `docker compose config --format json` dengan password tiruan untuk base dan kedua override (sesuai spec, termasuk `$$PGDATA` dan tmpfs yang hanya menyisakan mount init). Karena suite integrasi tidak boleh dijalankan di sesi ini (Docker bersama), saya menilainya lewat pembacaan kode, `verify.md`, dan menghitung 38 tes; saya juga memeriksa secara read only bahwa tidak ada container, volume, atau network `foundation-test*` yang tersisa. Dua perilaku yang hanya ditegaskan di spec dan `verify.md` saya buktikan sendiri di direktori scratch di luar repo, memakai perintah `docker` tiruan: (1) prompt konfirmasi `db:reset` lewat pty (jawaban salah, Ctrl+C, Ctrl+D keluar `1` tanpa `down`; nama volume yang tepat menjalankan `down --volumes` lalu `up`), dan (2) penanganan sinyal harness di bawah `bun test` sungguhan (SIGINT dan SIGTERM, baik saat test berjalan maupun saat `compose up` masih berjalan, menjalankan `down --volumes --remove-orphans` dan keluar `130` atau `143` tanpa `afterAll`). Keduanya berperilaku seperti klaim spec.

## Minor
### 🟡 `.env` belum diabaikan git di branch ini, `.gitignore:1`
**Problem**: `.gitignore` tidak punya aturan untuk `.env` (`git check-ignore -v .env` tidak menemukan apa pun). Spec 0002 (fitur 3, branch lain) menambahkan `.env`, `.env.*`, dan `!.env.example`, sehingga kekosongan ini disengaja dan `.env.example` hanya berisi bagian spec 0003 juga sesuai spec. Tetapi fitur ini sudah menetapkan `.env` sebagai tempat tiga password (komentar di `infrastructure/compose.yaml`, pesan `set POSTGRES_ADMIN_PASSWORD in .env`, loader `scripts/env-file.ts`).
**Why it matters**: Selama branch ini masuk `main` lebih dulu daripada fitur 3, `git add .` atau `git add -A` setelah developer membuat `.env` akan men-stage tiga password, dan hook pre-commit (`bun run check`) tidak menolaknya. AC-1 menyatakan tidak ada credential di repo; jaminan itu sementara bergantung pada kehati-hatian developer.
**Suggested fix**: Catat urutan merge secara eksplisit (fitur 3 sebelum fitur 5, atau keduanya bersamaan) di catatan scope atau deskripsi PR. Bila fitur 5 harus mendarat lebih dulu, tambahkan tiga baris `.gitignore` yang identik dengan yang ada di spec 0002 sehingga penggabungan nanti bersih tanpa konflik.

### 🟡 `stop()` tidak bisa diulang setelah `down` gagal, dan menutupi pesan kegagalan awal, `scripts/testing/postgres.ts:235`
**Problem**: `stop` mengisi `stopped = true` dan melepas dirinya dari `activeStops` sebelum `docker compose down` dijalankan (baris 235 sampai 238). Bila `down` gagal (daemon sedang bermasalah, network masih dipakai), `stop` melempar error, tetapi pemanggilan berikutnya (dari `afterAll`, atau dari handler SIGINT/SIGTERM) langsung `return` karena `stopped` sudah `true`. Di jalur kegagalan `up` (baris 250 sampai 255), `stop()` dipanggil sebelum `throw new Error('postgres in ... did not become healthy ...')`; bila `stop()` ikut melempar, pesan yang berisi stderr dan 50 baris log container hilang dan yang tampil hanya `docker compose down failed`.
**Why it matters**: Project sementara yang sudah gagal dihapus tidak dicoba lagi dan baru disapu oleh pembersih stale dua jam kemudian; selama itu container dengan data di tmpfs (memori) tetap hidup. Saat `up` gagal, diagnosis akar masalah (log init) justru yang tertutup. Spec hanya meminta `stop` idempoten; keduanya masih sesuai huruf spec, tetapi tidak sesuai niat AC-6 (resource dihapus walau ada kegagalan).
**Suggested fix**: Tandai `stopped` hanya setelah `down` berhasil (atau kembalikan ke `false` saat gagal) supaya pemanggilan berikutnya mencoba lagi. Di jalur `up` gagal, bungkus `stop()` dengan `try/catch` dan gabungkan kedua pesan agar pesan "did not become healthy" dan log tetap sampai ke developer.

### 🟡 Pagar AC-6 bergantung pada setiap pemanggil `runDb` mengingat `COMPOSE_PROJECT_NAME`, `tests/integration/postgres.test.ts:96`
**Problem**: `dbEnv` (baris 84) selalu menyetel `COMPOSE_PROJECT_NAME`, begitu pula dua pemanggil lain, sehingga hari ini tidak ada tes yang menyentuh `foundation-rust`. Tetapi `runDb` sendiri tidak memeriksa apa pun; `dbEnv(database, extra)` bahkan membiarkan `extra` menimpa nama project. Satu tes baru yang lupa menyetel variabel itu akan menjalankan `up`, `down`, atau `reset` terhadap project development developer (`reset` tetap butuh `--confirm=<nama volume>`, tetapi `up` dan `down` tidak).
**Why it matters**: Invarian paling penting spec ini adalah "test tidak pernah menyentuh project `foundation-rust`" (AC-6, key invariants). Invarian itu sekarang hanya terjaga oleh disiplin, padahal biaya kesalahannya adalah data atau container development developer.
**Suggested fix**: Di `runDb` (dan di `composeDown` pada baris 581), tolak dengan error bila `env.COMPOSE_PROJECT_NAME` tidak cocok dengan `^foundation-test-[0-9a-f]{16}$`. Ini satu baris dan menjadikan pelanggaran gagal keras saat tes ditulis, bukan saat data hilang.

### 🟡 Perlindungan log password di script init tidak dikunci test, `infrastructure/postgres/initdb/10-roles.sh:16`
**Problem**: Password masuk ke teks statement (psql menginterpolasi `:'migrator_password'` di sisi klien), jadi satu-satunya hal yang mencegah `CREATE ROLE ... PASSWORD '<nilai>'` tercatat di log server saat SQL gagal adalah `SET log_min_error_statement = 'panic'` dan `SET log_statement = 'none'` (baris 16 dan 17). Test statis di `scripts/db.test.ts:476` memeriksa `\getenv`, heredoc bertanda kutip, dan tidak adanya `PASSWORD '` literal, tetapi tidak memeriksa kedua `SET` itu; test dinamis "a failed init script never reports healthy" (`tests/integration/postgres.test.ts:535`) hanya menguji penjaga `bash` sebelum SQL, bukan kegagalan SQL. Begitu juga `REVOKE CONNECT ON DATABASE postgres FROM PUBLIC` (baris 23) dan `REVOKE ALL ON SCHEMA public FROM PUBLIC` (baris 27) tidak diperiksa oleh test mana pun.
**Why it matters**: Menghapus atau mengubah kedua `SET` saat refactor tidak membuat test gagal, padahal akibatnya password role bocor ke `docker logs` pada init yang gagal; ini tepat jenis kebocoran yang diklaim dicegah oleh spec (security model: tidak muncul di SQL, argumen, atau log statement).
**Suggested fix**: Tambahkan ke test statis pernyataan bahwa kedua `SET` ada dan muncul sebelum `CREATE ROLE`; bukti dinamis sulit dibuat karena password yang lolos validasi tidak membuat SQL gagal, jadi kunci statis sudah cukup. Tambahkan juga ke suite integrasi satu pemeriksaan bahwa koneksi ke database `postgres` sebagai `foundation_app` ditolak (SQLSTATE `42501`) dan satu pemeriksaan hak PUBLIC pada schema `public` (misalnya `has_schema_privilege` untuk role lain tanpa grant).

### 🟡 Jalur konfirmasi interaktif `db:reset` tidak punya test otomatis, `scripts/db.ts:155`
**Problem**: `promptLine`, cabang `process.stdin.isTTY` di `readConfirmation` (baris 194), serta daftar dan pelepasan listener `SIGINT` dan `close` hanya dibuktikan secara manual di `verify.md`. Semua test otomatis menjalankan `reset` tanpa terminal (stdin tertutup atau pipa), sehingga cabang TTY (jalur yang benar-benar dipakai developer) tidak pernah dieksekusi oleh `bun test`.
**Why it matters**: Ini satu-satunya pengaman perintah yang paling destruktif, dan di dalamnya ada logika status (`settled`, tiga sumber penyelesaian: jawaban, `close`, SIGINT) yang mudah rusak saat Bun atau Node mengubah perilaku readline. Hasil pty saya hari ini cocok dengan spec, tetapi tidak ada yang akan memberi tahu bila nanti berubah.
**Suggested fix**: Tambahkan tes pty kecil di `scripts/db.test.ts` yang memakai `docker` tiruan yang sudah ada (`FAKE_DOCKER`): jawaban salah, Ctrl+C, dan Ctrl+D menghasilkan status `1` tanpa panggilan `down`; nama volume yang tepat menghasilkan urutan `config`, `down --volumes`, `up`. Bila pty sulit dipasang di CI, cukup satu tes yang menjalankan `script(1)` di Linux dan macOS, dengan skip eksplisit di platform lain.

## Nits

Dampaknya kecil (tidak ada hak tulis permanen) dan kode cocok dengan spec, jadi ini bukan cacat implementasi; saya belum membuktikannya di container, hanya dari default PostgreSQL. Bawa ke `/architect` bila ingin menutupnya.
- ⚪ `scripts/db.ts:128`, `docker info` dijalankan tanpa `timeout`; daemon yang setengah hidup (Docker Desktop saat start) membuat setiap perintah `db:*` menggantung tanpa pesan. Batas 10 sampai 15 detik dengan pesan "Docker is not running" cukup.
- ⚪ `scripts/db.ts:57`, `validateInfraEnv` mengembalikan `port` yang tidak dibaca pemanggil produksi mana pun (`main` hanya memeriksa `ok`; Compose membaca `POSTGRES_PORT` sendiri). Nilainya hanya dipakai test dan nanti fitur 4; wajar, tetapi beri komentar singkat agar tidak terlihat sebagai kode mati.
- ⚪ `scripts/testing/postgres.ts:284`, `PGPASSWORD=<password>` dilewatkan sebagai argumen `docker compose exec -e`, sehingga terlihat di `ps` host selama tes. Spec sendiri menetapkan bentuk ini dan password-nya acak serta hanya berlaku di project sementara, jadi ini bukan temuan; tetapi huruf invarian "tidak ada credential di argumen proses" tidak sepenuhnya benar untuk harness. Bila Compose mendukung `-e PGPASSWORD` tanpa nilai (diambil dari env anak), pakai itu; bila tidak, cukup kecualikan harness di teks invarian spec.
- ⚪ `scripts/testing/postgres.ts:149`, pembersih stale hanya melihat container. Network atau volume sebuah project yang container-nya sudah hilang (proses mati di antara langkah `down`) tidak pernah disapu. Jarang terjadi; cukup dicatat.
- ⚪ `package.json:24`, suite integrasi tidak punya task root dan tidak dijalankan CI; `bunfig.toml` (`[test] root = "scripts"`) membuat `bun test` polos melewatinya, sehingga hanya perintah panjang di komentar kepala `tests/integration/postgres.test.ts` yang menjalankannya. Spec tidak menamai task, dan fitur 4 berencana memindahkan tes integrasi ke `tests/integration/`, jadi ini tindak lanjut, bukan kesalahan.
- ⚪ `AGENTS.md`, blok Commands belum memuat `db:up`, `db:down`, `db:status`, `db:reset`, perintah suite integrasi, dan fakta bahwa `bun run test:scripts` sekarang butuh CLI `docker` dengan plugin Compose (belasan tes `docker compose config`). Itu wilayah `/sync`, jangan lupa saat langkah berikutnya.
- ⚪ `infrastructure/compose.test.yaml:5`, dan `compose.test-tmpfs.yaml` memakai tag `!override`, yang butuh Compose terbaru, begitu pula `start_interval` di healthcheck yang butuh Docker Engine yang cukup baru. Di Compose lama kegagalannya berupa galat parsing YAML yang tidak menyebut versi. Spec 0001 sudah mengusulkan Compose `v5.5.1` atau lebih baru, tetapi tidak ada pemeriksaan atau catatan di `db.ts` maupun harness; satu kalimat di bantuan atau pesan galat sudah cukup.

## Strengths
- Kecocokan dengan spec sangat rapat dan dikunci test: teks SQL init, blok `.env.example` (dibandingkan persis), tabel pesan validasi per baris, argumen Compose, nama volume dari `docker compose config` (bukan dirangkai string), dan override tmpfs yang hanya menyisakan mount init. Saya mencocokkan setiap bagian build spec dengan kode dan tidak menemukan keputusan baru yang tidak dinamai spec.
- `scripts/db.ts` dibelah dengan benar: fungsi murni (`validateInfraEnv`, `buildComposeArgs`, `confirmationAccepted`, `composeEnv`, `volumeNameFromConfig`) diuji langsung, sedangkan efek samping diuji di batas proses dengan `docker` tiruan yang mencatat argumen, env, dan cwd. Pemetaan status keluar (Compose diteruskan, sinyal `128 + n`, validasi dan Docker `1`) dan semua jalur gagal `reset` (config gagal, `down` gagal, volume tidak terbaca) punya tes.
- Pengaman `db:reset` konservatif: tanpa terminal dan tanpa `--confirm=<nama>` yang persis, selalu menolak; `--confirm <nama>` dengan spasi, argumen ekstra, dan nilai kosong ditolak; `confirmationAccepted` menolak nama harapan kosong. Konfirmasi dibandingkan dengan nama volume efektif dari Compose sehingga `COMPOSE_PROJECT_NAME` tidak bisa mengelabui pesan.
- Harness menangani pembersihan dengan sungguh-sungguh: pendaftaran sebelum `up`, `stop` idempoten, penolakan nama non `foundation-test-`, pembersih stale yang konservatif (pola nama, semua container lebih tua dari dua jam, tanggal tak terbaca dianggap tidak stale), dan handler sinyal yang terbukti jalan di bawah `bun test` (termasuk saat `compose up` masih berjalan) dan di fixture proses terpisah. Bentuk keluaran `docker inspect --format` yang diasumsikan pembersih sesuai dengan keluaran Docker nyata (saya periksa read only pada satu container yang sudah ada).
- Tes hak role bermutu: kontrol positif pada tabel dan sequence buatan migrator (identity untuk membuktikan hak sequence) di dua schema, delapan operasi DDL dan administrasi yang ditolak `42501`, `pg_roles`, ACL `PUBLIC` lewat `aclexplode` dengan penjaga ACL kosong, aturan `pg_hba` seluruhnya `scram-sha-256`, dan password salah di ketiga role (status `2`).
- Tes kegagalan init (password migrator pendek) membuktikan container tidak pernah `healthy` dan log tidak memuat nilai password; tes "Docker tidak terjangkau" dan "port host terpakai" membuktikan pesan error nyata, bukan hanya jalur bahagia.
- Loader env kecil dan jujur: path default dihitung dari lokasi script (diuji dari direktori lain), nilai env non kosong menang, nilai kosong diisi dari file, tidak ada ekspansi `$VAR`, dan galat membaca menyebut path. Saya juga memastikan `bun run <task>` tidak memuat `.env` ke env anak walau task memakai `--no-env-file`, sehingga satu-satunya jalur muat adalah loader ini.
- Disiplin konvensi: tidak ada dependency baru, ekspor bernama saja, kode dan pesan error berbahasa Inggris, dokumen berbahasa Indonesia, `bun run check` bersih termasuk `tsc -p tests/tsconfig.json` dan ESLint strict untuk `tests/`.
